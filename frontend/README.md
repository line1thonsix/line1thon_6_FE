# Deveil frontend

React + TypeScript + Vite + Tailwind CSS 기반의 PC UI입니다.
질문 입력 → 답변 잠금 → 생각 제출 → 분석·재시도 → 관점 비교 결과까지 MSW로 동작합니다. 실제 백엔드·AI는 연결하지 않았습니다.

## 실행

```sh
npm install
npm run dev:mock
```

Vite가 출력하는 주소로 접속합니다. 기본 포트는 5173입니다.
`npm run dev`는 UI만 실행하며, Mock 모드가 아니면 질문 전송을 안내 메시지로 차단합니다.
프로덕션 빌드에서도 Mock API를 호출하거나 Worker를 시작하지 않습니다.

```sh
npm run build     # TypeScript 검사 + 프로덕션 빌드
npm run lint
npm test          # 검증 경계값·잠금 데이터·중복 생성·오류 재시도 테스트
npm run preview
```

## Mock 시나리오

Mock 서버에서 다음 URL 매개변수를 사용합니다. 실제 서비스 요청 계약에는 포함되지 않습니다.

- `/`: 약 1.2초 후 질문 생성 성공, LOCKED 상태
- `/?mock=error-once`: 첫 요청 실패, 같은 요청 재시도 시 성공
- `/?mock=error`: 계속 실패
- `/?mock=slow`: 약 5초 후 성공 (로딩·새 채팅 중 요청 취소 검증)

MSW는 개발 모드의 `VITE_ENABLE_MOCKS=true`일 때만 동적 로드합니다.
`.env.mock`이 이를 활성화합니다. 또는 `.env.example`을 `.env.local`로 복사해 설정할 수 있습니다.
F-13 복구는 같은 탭의 `sessionStorage`를 사용합니다. 질문·코드·유형과 생각 초안을 즉시 임시 저장하며, 탭을 닫거나 브라우저 저장소를 지우면 사라집니다.
제출 후에는 대화 ID로 GET 상세를 다시 조회하고 서버의 생각·분석 작업을 복원합니다. 분석 상태는 기존 2초 폴링으로 재확인하며 FAILED/DONE에서도 재시작하거나 시도 횟수를 초기화하지 않습니다.
질문 전송 응답을 받기 전 새로고침하면 동일 요청 ID로 POST를 재전송합니다. 서버의 멱등성 처리가 필요합니다.
복원 실패 시 오류와 다시 불러오기 버튼을 표시하며, 새 채팅으로 이동할 수도 있습니다.

### 상태 저장과 실제 API 경계

- `deveil:mock:workspace:v1`: 질문 초안, 대화 ID 또는 진행 중 질문 요청 ID. 답변·비교 결과를 저장하지 않습니다.
- `deveil:thought-draft:v1:<chatId>`: 제출 전 생각 초안. 성공 응답 시 제거합니다. 제출 후 복원에서는 서버 생각이 우선입니다.
- `deveil:mock-server:v1:*`: **개발 전용 MSW 가상 서버**의 대화·생각·분석 시각·시도 횟수·멱등성 정보. 새로고침 테스트를 위한 대체 저장소이며 실제 서버나 보안 경계가 아닙니다. 답변·비교 결과는 저장하지 않습니다.
- 실제 API 모드는 Mock 저장소를 읽거나 MSW를 실행하지 않습니다. 현 시점의 API 함수는 Mock 전용이며 실제 API 연결은 차단합니다. 백엔드 계약 확정 후 별도 어댑터와 서버 저장·권한 검증을 연결해야 합니다.
- 실제 답변 데이터는 번들·브라우저 저장소에 선탑재하지 않습니다. 개발용 가짜 응답 모듈도 DEV 조건의 동적 import 아래에 있으며 프로덕션 빌드에서 제외됩니다.

### 저장 응답 시연

`npm run dev:mock` 실행 후 `/?demo=true&analysis=always-fail`로 접속하고 예시 카드 3개 중 하나를 선택합니다.
생각을 제출하면 AI 실패를 모사한 뒤 해당 질문의 저장 응답을 사용하고 결과에 **저장 예시** 태그를 표시합니다.
`fail-once`, `fail-twice`, `invalid-output`, `timeout` 실패 시나리오에도 적용됩니다. 일반 성공에는 태그가 붙지 않습니다.
정확히 일치하는 질문·유형, 빈 코드인 예시만 대상입니다. 자유 질문·변경한 코드에는 적용하지 않습니다.
저장 응답의 비교 항목은 실시간 분석으로 꾸미지 않고 판단 보류·직접 검증 안내로 표시합니다. 시연 선택은 대화 생성 시 고정됩니다.
실서비스의 저장 답변은 반드시 서버에서 보관하고 DONE 이후 잠금 검사를 통과한 별도 결과 API로만 내려줘야 합니다.

## 현재 범위

- 질문 유형 5개, 질문 1~2,000자·선택 코드 최대 6,000자
- Enter 전송, Shift+Enter 줄바꿈, IME 조합 중 전송 방지
- 예시 질문 카드는 해당 유형으로 즉시 전송 (작성 중 코드 대신 예시 자체를 전송)
- 코드 접기·펼치기와 확대, 코드 미실행
- 전송 후 질문·코드·유형 변경 금지, 중복 전송 즉시 차단
- 오류 시 질문·코드 보존, 동일한 Mock 요청 ID로 재시도
- 새 채팅 시 진행 중 요청 취소, 늦은 응답 무시
- 잠금 화면의 선택지 3개·예시 문장을 내 생각 초안에 삽입
- 내 생각 30~2,000자·다양성 검증, 분석 최대 3회, DONE 이후 결과·5개 분류·근거 펼침
- 힌트·영구 학습 기록 등 P1/P2는 미구현

잠금 배경은 장식용 선입니다. 기준 답변·분석 결과는 잠금 응답에 없으며, 별도 결과 API도 DONE 이전에는 거부합니다.
응답을 UI 상태로 옮길 때도 공개 가능한 필드만 새 객체에 복사합니다.
코드·유형 선택과 내 생각 제출 버튼은 전송 후 적절히 비활성화합니다.

## 구조와 임시 계약

- `src/components/ui`: Button, Card, Input, Textarea, Icon
- `src/components/layout`: AppShell, Sidebar, Header
- `src/components/chat`: 입력창, 코드 에디터, 유형 선택, 질문 말풍선, 잠금 카드
- `src/hooks/useQuestionFlow.ts`: 입력·로딩·오류·잠금 상태와 요청 수명 관리
- `src/styles/tokens.css`: 디자인 토큰 (PC 1440×900 기준)
- `src/types/chat.ts`: 프론트 화면 모델
- `src/api/mockChatContract.ts`: 개발 전용 임시 경로·요청 타입
- `src/api/chats.ts`: Mock 전용 HTTP 어댑터
- `src/api/lockedChat.ts`: 잠금 응답 허용 필드 투영
- `src/mocks`: 질문 생성·잠금 상세 조회 핸들러와 답을 포함하지 않는 fixture
- `tests/question-flow.test.mjs`: Node 내장 테스트와 MSW 통합 검증

`POST /api/chats`와 `GET /api/chats/:chatId`의 응답 구조·clientRequestId는 이번 UI용 임시 Mock 계약입니다.
실제 서버의 인증(쿠키/헤더), DTO, 중복 방지 규약, 생성 상태 조회와 오류 계약은 확정하지 않았습니다.
실제 연동 때 HTTP 어댑터와 Mock 계약을 교체해야 합니다. 이번 Mock의 접근 제어는 실제 서버 보안 검증을 대신하지 않습니다.

게스트 자동 저장 문구는 Figma 문구이며 이번 단계에는 영구 저장 기능이 없습니다.
폰트는 SF Pro 우선, 없으면 OS 대체 글꼴을 사용하며 모바일 디자인은 이번 범위가 아닙니다.
BrowserRouter 배포 시 정적 호스트에 SPA fallback 설정이 필요합니다.
`VITE_` 환경 변수에는 비밀키를 넣지 마세요. `../docs`는 변경하지 않습니다.

## F-13 직접 테스트: 6가지 시나리오

```sh
cd /Users/choejiwon/Documents/deveil/frontend
npm run dev:mock -- --host 127.0.0.1 --port 5174 --strictPort
```

5174가 사용 중이면 기존 Mock 서버를 사용하거나 포트를 바꿉니다. 아래 경로는 실행한 서버 주소 뒤에 붙입니다.
각 테스트를 시작할 때 **URL 설정 → 새 채팅 클릭** 순서를 지킵니다. URL 변경만으로 기존 대화가 초기화되지는 않습니다.
복구 검증은 **같은 탭에서 새로고침**합니다. 새 탭·다른 포트·탭 닫기 후 재접속은 같은 sessionStorage를 보장하지 않습니다.

공통 생각 입력 예시(그대로 제출 가능):

> 먼저 입력 조건과 실행 순서를 확인하고 작은 예시에서 실제 값을 출력해서 기대한 결과와 비교해 볼게요.

| 번호 | 경로 | 실행 방법 | 기대 결과 |
| --- | --- | --- | --- |
| 1. 작성 중 초안 | `/` | 새 채팅에서 질문·코드·유형을 작성하고 전송 전 새로고침. 이어 질문을 전송하고 생각을 작성한 뒤 제출 전 새로고침 | 질문·코드·유형과 생각 초안 각각 복원. 아직 AI 답변 비공개 |
| 2. 잠금 복구 | `/` | 질문을 전송하고 잠금 화면이 뜨면 생각을 제출하지 않은 상태로 새로고침 | 같은 질문·코드·선택지·예시 문장과 잠금 유지. 분석은 시작하지 않음 |
| 3. 분석 중 폴링 재개 | `/?analysis=slow` | 질문 → 생각 제출 → 분석 중 표시 후 30초가 되기 전에 새로고침 | 같은 생각·작업·1/3 시도 유지, 2초 간격 GET 재개. 최초 분석 시작 기준 약 30초 후 완료(조회 간격에 따른 표시 차이 있음). 새로고침마다 30초를 다시 세지 않음 |
| 4. 실패·재시도 유지 | `/?analysis=always-fail` | 질문 → 생각 제출 → 약 6초 후 실패. 새로고침, 다시 연결 버튼 클릭. 총 3회까지 반복 | 생각과 실패 상태 보존. 재시도 시 2/3, 3/3. 3회 실패 후 재시도 불가·답변 계속 잠금. 새로고침으로 시도 횟수 초기화 불가 |
| 5. 완료 복구 | `/` | 질문 → 생각 제출 → 결과가 보이면 새로고침 | 같은 최초 생각과 비교 결과를 재조회. 새 분석 시작·추가 시도 없음. 필터/근거 펼침 선택 자체의 복원은 범위 밖 |
| 6. 저장 예시 시연 | `/?demo=true&analysis=always-fail` | 새 채팅 → 예시 카드 선택 → 생각 제출 → 약 6초 후 결과 확인 → 새로고침. 카드 3개를 각각 새 채팅으로 반복 | 각 질문에 맞는 저장 응답과 `저장 예시` 태그 유지. 자유 질문·유형 변경·코드 추가에는 적용 안 됨. 실제 AI 호출 없음 |

4번에서 재시도 후 성공도 확인하려면 `/?analysis=fail-once`로 새 채팅을 시작합니다. 1회 실패 후 2회차에서 정상 완료합니다.
6번에서 `demo=true`를 빼고 새 채팅을 시작하면 같은 예시 질문도 실패하며 저장 응답을 사용하지 않습니다.

### 실패·지연 옵션 목록

모든 옵션은 DEV + `VITE_ENABLE_MOCKS=true`에서만 유효합니다. `npm run dev`/프로덕션에서는 활성화되지 않습니다.

| 옵션 | 동작 |
| --- | --- |
| `mock=error-once` / `mock=error` | 질문 생성 첫 요청만 실패 / 계속 실패. 질문·코드 보존 및 같은 요청 재시도 확인 |
| `mock=slow` | 질문 생성 응답 약 5초 지연 |
| `thought=error-once` / `thought=error` | 생각은 가상 서버에 저장하지만 제출 응답을 첫 회만 / 계속 실패시킴. 새로고침하면 서버 저장 상태로 복원되므로 실패 UI 대신 분석·결과로 갈 수 있음 |
| `thought=slow` | 생각 제출 응답 약 5초 지연. 저장·분석 시작은 응답 전에 이루어져, 응답 직후 이미 완료일 수 있음 |
| `analysis=slow` | 정상 분석 30초 지연. 폴링·새로고침 테스트용 신규 옵션 |
| `analysis=fail-once` / `analysis=fail-twice` | 첫 1회 / 2회 분석 실패 후 사용자가 재시도하면 성공 |
| `analysis=always-fail` | 모든 분석 시도 실패. 각 시도 약 6초, 최대 3회 |
| `analysis=invalid-output` | 약 6초 후 유효하지 않은 분석 응답 오류 |
| `analysis=recover` | 내부 재호출 후 약 6초에 성공, 사용자 시도는 1회 |
| `analysis=pending` / `analysis=timeout` | 두 옵션 모두 분석을 완료하지 않고 약 90초 후 TIMEOUT 실패. 무한 대기 옵션이 아님 |
| `result=fetch-error` | 분석은 DONE이지만 별도 결과 조회가 503으로 실패. `result` 옵션을 제거해 같은 탭에서 다시 접속하면 기존 결과를 조회 가능 |
| `result=empty` / `result=all-invalid` | 빈 결과 / 원문 인용이 모두 잘못된 결과. 분석 INVALID_OUTPUT 실패, 계속 잠금 |

옵션 조합 예: `/?mock=slow&thought=error-once&analysis=slow`.
분석 시나리오는 작업 생성 시 저장되며, URL 변경이 진행 중인 작업을 바꾸지 않습니다. 시연 여부·결과 fixture는 대화 생성 시 저장됩니다.
`result=fetch-error`는 결과 조회 때 읽으므로 기존 대화에서도 켜고 끌 수 있습니다.
개발자 도구 Network에서 `/analysis` 조회의 약 2초 간격과 같은 jobId/attempt를 확인할 수 있습니다.
복원 시 분석 상태를 즉시 조회하고 FAILED/DONE이면 반복 폴링을 중단합니다. 화면 복구 시점에 이미 완료되었다면 분석 로딩은 짧게 보일 수 있습니다.
